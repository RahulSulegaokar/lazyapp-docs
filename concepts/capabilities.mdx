Meta does not open every WhatsApp feature to every account. India payments, opt-in links and groups are switched on per business, sometimes per number, and sometimes only in certain countries. A few features, such as calling, also wait on Meta approving LazyApp itself.

So LazyApp does not let you hard-code that knowledge. Ask:

```bash
curl https://lazyapp.in/v1/capabilities \
  -H "Authorization: Bearer $LAZYAPP_API_KEY"
```

```json
{
  "data": [
    {
      "connection_uuid": "9f8b1c2d-4e5f-4a6b-8c7d-0e1f2a3b4c5d",
      "phone_number_id": "123456789012345",
      "display_phone_number": "+919812345670",
      "is_default": true,
      "quality_rating": "GREEN",
      "messaging_limit_tier": "TIER_1K",
      "capabilities": {
        "messages.text": true,
        "messages.template": true,
        "flows": true,
        "calling": false,
        "block_users": true,
        "groups": false,
        "messages.group": false,
        "commerce.catalog_sync": true
      }
    }
  ]
}
```

## Why a capability is false

Two different reasons, and the distinction matters:

- **Meta has not granted it yet.** Calling starts `false` for everyone, because Meta has not yet approved calling for LazyApp's app. Once it does, LazyApp turns it on per connection — no deploy on your side, no code change. Your integration should start working the moment the flag flips.
- **Your number does not qualify yet.** `groups` and `messages.group` need an Official Business Account. [`POST /v1/groups/eligibility`](/guides/groups#before-you-start) checks Meta and flips both flags to match.
- **Switched off for one connection.** Block lists (`block_users`) and catalog sync default on; a connection can turn either off.

Either way the correct client behaviour is the same: read the flag, and degrade gracefully when it is `false`.

## Feature status

These docs use two labels for features you cannot use straight away. The difference is who has to say yes.

**Available once Meta approves your account.** LazyApp supports the feature today. Meta switches it on for each business, so it works as soon as Meta approves yours:

| Feature | What Meta looks for |
| --- | --- |
| [India payments](/guides/payments-india) | An Indian business that has accepted WhatsApp's payment terms, with a payment setup Meta has made active |
| [Opt-in links](/guides/growth-tools#opt-in-links-in-app-signup) | A business outside the markets where Meta does not offer them |
| [Group chats](/guides/groups) | The blue tick (Official Business Account) on a Cloud API number |
| [Marketing Messages](/sending/marketing-messages) features | Meta's marketing terms accepted and a payment method on the WhatsApp account |
| [Direct Send](/sending/direct-send) | A messaging limit of 100,000 or unlimited for utility messages; an approved application to Meta for login codes |

**Coming soon.** LazyApp has built the feature, and it is waiting on Meta approving LazyApp's own Meta app. Nothing is needed from you, and no code change will be needed when it arrives:

| Feature | What LazyApp is waiting for |
| --- | --- |
| [Calling](/guides/calling) | Meta's calling approval for LazyApp's app |
| The `message_echoes` webhook (messages another app sends from your number) | Advanced access to that webhook for LazyApp's app |
| Ad spend in [ad results](/guides/ad-results) | Meta's `ads_read` permission for LazyApp |
| Editing your catalog from LazyApp ([Manage products](/sending/catalog-inventory)) | Meta's `catalog_management` permission for LazyApp |
| Multi-Partner Solutions (sharing a number with another Meta partner) | Meta's Solution Partner status for LazyApp |

## Using it well

<CodeGroup>
```js Node
const { data } = await lazyapp('/v1/capabilities');
const number = data.find((c) => c.is_default);

if (number.capabilities.calling) {
  showCallButton();
}
```
</CodeGroup>

<Tip>
  Cache the response for a few minutes rather than calling it per send. It changes rarely,
  but do not cache it for the life of your process — the point is that it can change
  without you deploying.
</Tip>

## Quality rating

`quality_rating` is Meta's own signal — `GREEN`, `YELLOW` or `RED` — reflecting how recipients are reacting to your messages. A number sliding to `RED` risks having its messaging limit cut, so it is worth alerting on. You also receive `phone_number.quality_changed` [webhooks](/webhooks/events).

## Messaging limit tier

`messaging_limit_tier` is Meta's send ceiling for that number (for example `TIER_1K`). It moves as quality and usage change. Pair it with `quality_rating` when you decide how aggressively to run broadcasts.
