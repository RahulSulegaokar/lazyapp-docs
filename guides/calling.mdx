WhatsApp Business Calling lets customers call your business number from the chat, and lets you call customers who have said you may. LazyApp handles the **signalling**: it relays the call setup to Meta, keeps call history, records and transcribes calls when you ask, and sends [`call.*` webhooks](/webhooks/events#calls). The audio itself runs in a browser or on your own WebRTC or SIP system, never through LazyApp.

<Warning>
**Coming soon.** Calling is built and follows Meta's current calling docs, but Meta has not yet approved calling for LazyApp's own Meta app, so no number can use it yet. When Meta approves it, calling switches on with no change on your side. Until then, [`GET /v1/capabilities`](/concepts/capabilities) reports `calling: false` and the call endpoints answer `422` with `code: capability_unavailable`. Meta also requires each number to have a messaging limit of at least 2,000 customers a day. See [feature status](/concepts/capabilities#feature-status).
</Warning>

## Two ways to take calls

| | Inbox softphone | Your own client |
| --- | --- | --- |
| Who it is for | Teams answering calls themselves | Contact centres, IVRs, AI voice agents |
| Where audio runs | The agent's browser (WebRTC) | Your WebRTC media server, or a SIP server |
| Setup | Nothing. Calls ring in the inbox | Build the peer connection and call the API below |

### In the inbox

While the inbox is open, an incoming call rings in the corner with **Answer** and **Decline**. To call someone, open their chat and click the phone button. If they have not allowed calls yet, LazyApp offers to send them a permission request first. You can switch on **Record and transcribe** before answering or calling.

The browser asks for microphone access the first time.

#### Why calls need a TURN server

Call audio travels directly between the agent's browser and Meta. Many office and mobile networks block that direct path. A TURN server relays the audio around the block, so the call still has sound. Before every call, the inbox asks LazyApp for short-lived TURN login details, which expire on their own; the shared secret behind them never reaches the browser. If no TURN server is set up, the call card says plainly that calls may have no sound on some networks.

## Settings

Turn calling on, hide or show the call button, set call hours, ask for permission to call back, and set up voicemail in **Connections → number → Calling**. The same settings are available over the API:

```bash
curl -X PATCH https://lazyapp.in/v1/connections/$CONNECTION_UUID/calling-settings \
  -H "Authorization: Bearer $LAZYAPP_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "calling": {
      "status": "ENABLED",
      "call_icon_visibility": "DEFAULT",
      "callback_permission_status": "ENABLED"
    }
  }'
```

`calling` takes Meta's own fields: `status`, `call_icon_visibility`, `call_icons.restrict_to_user_countries`, `callback_permission_status`, `call_hours`, `audio.additional_codecs` (`PCMA`, `PCMU`), `srtp_key_exchange_protocol` (`DTLS` or `SDES`), `voicemail` and `sip`. The settings never include the SIP password; read it [separately](#your-own-phone-system-sip).

<Note>
The inbox softphone needs `DTLS`, the default. Choose `SDES` only for a SIP server.
</Note>

### Voicemail

With voicemail on, a call you decline, or that rings for `timeout_seconds` (0 to 30 seconds, Meta's range), is answered by WhatsApp, which plays your greeting and records a message. The recording arrives as an ordinary inbound voice note with `content.voicemail.call_id`. Upload the greeting (OGG/Opus, under 60 seconds) in the calling settings. Turn call hours off to use voicemail: customers cannot ring outside call hours.

### Your own phone system (SIP)

If you already run a phone system or contact centre, connect it over SIP instead of using the inbox. WhatsApp then sends calls to your SIP server, and your agents answer them there. In the console this is **Use your own phone system (SIP)** in the calling settings.

```json
{
  "calling": {
    "sip": {
      "status": "ENABLED",
      "servers": [ { "hostname": "sip.acme.example", "port": 5061 } ]
    },
    "srtp_key_exchange_protocol": "SDES",
    "audio": { "additional_codecs": ["PCMA", "PCMU"] }
  }
}
```

- Meta takes **one SIP server per number**. An empty `servers` list removes it.
- `port` defaults to 5061, SIP over TLS.
- `audio.additional_codecs` adds G.711 (`PCMA`, `PCMU`) for phone systems that need it.
- `srtp_key_exchange_protocol` sets how the call is encrypted: `DTLS` or `SDES`.
- `webhook_delivery` turns on Meta's SIP call webhooks. It is off unless you ask.

Meta generates a password for your SIP server to check each call. Read it when you set up the server:

```bash
curl -X POST https://lazyapp.in/v1/connections/$CONNECTION_UUID/calling-settings/sip-password \
  -H "Authorization: Bearer $LAZYAPP_API_KEY"
```

```json
{ "connection_uuid": "…", "sip_hostname": "sip.acme.example", "sip_username": "…", "sip_user_password": "…" }
```

It needs the `messages:send` scope, every read is recorded in the workspace audit log, and the answer is never cached. Before SIP is on with a server, the answer is `404` with `code: sip_not_configured`. In the console, people who can manage numbers see it under the calling settings. On the [Meta-compatible API](/migrating/from-cloud-api), `GET …/settings?include_sip_credentials=true` returns it as Meta does.

### Call link

Each number has a call link, `https://wa.me/call/<number>`, shown in the calling settings. Put it on your website or in an email; opening it starts a WhatsApp call.

## Permission to call

A business can only call someone who said yes. Check first:

```bash
curl "https://lazyapp.in/v1/calls/permissions?to=%2B919812345670" \
  -H "Authorization: Bearer $LAZYAPP_API_KEY"
```

```json
{
  "status": "temporary",
  "expires_at": "2026-10-27T10:00:00+00:00",
  "can_call": true,
  "can_request_permission": false,
  "actions": [ { "action_name": "start_call", "can_perform_action": true, "limits": [ … ] } ]
}
```

`to` can also be a business-scoped user id. `actions` is Meta's detail, including how many requests and calls you have left.

If `can_call` is false, ask. How the request goes out depends on the 24-hour customer service window:

- **Inside the window** (the person messaged you in the last 24 hours), it is an interactive message with your `body`.
- **Outside it**, WhatsApp accepts the request only as an approved template with **Ask permission to call** ticked and nothing to fill in. Name one with `template` and `template_language`, or LazyApp uses the oldest one that fits. With none, the answer is `422` with `code: call_permission_template_required` and a sentence that says what to create.

The response's `sent_as` is `interactive` or `template`.

```bash
curl -X POST https://lazyapp.in/v1/calls \
  -H "Authorization: Bearer $LAZYAPP_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "to": "+919812345670", "type": "call_permission_request", "body": "May we call you about your order?" }'
```

Their answer arrives as [`call.permission_request`](/webhooks/events#calls). WhatsApp allows one request a day and two a week per person.

## Answer a call (your own client)

1. `call.received` fires, and [`GET /v1/calls/{uuid}`](/api-reference/calls/retrieve-a-call) returns the caller's SDP offer as `session` (`type: offer`).
2. Create an SDP answer in your WebRTC stack and send it with `pre-accept`, so the media path is ready before the caller hears anything.
3. Send the **same** answer with `accept`. Meta rejects a different one.

```bash
curl -X POST https://lazyapp.in/v1/calls/$CALL_UUID/pre-accept \
  -H "Authorization: Bearer $LAZYAPP_API_KEY" -H "Content-Type: application/json" \
  -d '{ "sdp_answer": "v=0…" }'

curl -X POST https://lazyapp.in/v1/calls/$CALL_UUID/accept \
  -H "Authorization: Bearer $LAZYAPP_API_KEY" -H "Content-Type: application/json" \
  -d '{ "sdp_answer": "v=0…" }'
```

Decline with `POST /v1/calls/{uuid}/reject`.

## Place a call (your own client)

```bash
curl -X POST https://lazyapp.in/v1/calls \
  -H "Authorization: Bearer $LAZYAPP_API_KEY" -H "Content-Type: application/json" \
  -d '{ "to": "+919812345670", "type": "business_initiated", "sdp_offer": "v=0…" }'
```

Meta's SDP answer arrives on the calls webhook; poll `GET /v1/calls/{uuid}` until `session.type` is `answer` and apply it. If the person has not allowed calls, the response is `422` with `code: call_permission_missing`.

End any call with `POST /v1/calls/{uuid}/terminate`, even after your media path hung up: Meta prices calls from that signal.

### Media requirements

Meta's media stack is WebRTC-compatible but strict. Use Opus at 48 kHz with `ptime` 20, DTMF (`telephone-event`) at 8 kHz, and a single audio SSRC. Meta is ICE-lite, so your side takes the ICE controlling role and acts as the DTLS client. Meta provides no STUN or TURN servers.

## Recordings and transcripts

Ask for a recording, a transcript, or both, per call, on `accept` or on a business-initiated `POST /v1/calls`:

```json
{
  "recording": { "status": "ENABLED", "purpose": "quality and training", "announcement_language": "en_US" },
  "transcription": { "status": "ENABLED", "purpose": "quality and training", "announcement_language": "en_US" }
}
```

Both people hear a short notice built from `purpose` (up to 250 characters) before recording starts. `announcement_language` is one of `en`, `en_US`, `en_AU`, `en_CA`, `en_GB`, `en_IN`, `en_NZ`, `nl`, `fr`, `de`, `hi`, `it`, `kn`, `pt`, `es`, `es_ES`, `te`, `vi`.

About a minute after the call ends, LazyApp downloads both from Meta and sends `call.recording_available` and `call.transcript_available`. `GET /v1/calls/{uuid}` then reports:

```json
{
  "recording": { "available": true, "pending": false, "mime_type": "audio/ogg; codecs=opus" },
  "transcript": { "available": true, "pending": false, "language": "en", "text": "[Business] Hello… [Customer] Hi…" },
  "transcript_segments": [ { "speaker": "Business", "channel": 0, "start": 1.16, "end": 2.44, "text": "Hello…" } ]
}
```

Download the audio from `GET /v1/calls/{uuid}/recording`. It answers `409` with `code: recording_pending` while the download is still running, and `404` with `code: no_recording` when the call was not recorded.

## Call history

[`GET /v1/calls`](/api-reference/calls/list-calls) lists calls newest first, cursor-paginated. Each call has `direction`, `status` (`ringing`, `accepted`, `rejected`, `missed`, `terminated`, `failed`), the numbers, timestamps and `duration_seconds`.

## Pricing

Customer-initiated calls are free, and so are calls nobody answered. Business-initiated calls that connect are charged by Meta per six-second pulse (a part pulse counts as a whole one), at the per-minute rate of the country called, with volume tiers based on the minutes called that month. Meta bills them to your own Meta payment method, and LazyApp adds 0%. A call permission request is an ordinary message.

LazyApp records each connected business-initiated call with its billed seconds. Meta's call webhooks carry no price, so **Analytics → What WhatsApp counted** compares LazyApp's record with Meta's own daily count and cost of calls, and [`metric=calls`](/guides/whatsapp-analytics) returns Meta's numbers.
